Multi-Year Logistics Data Migration

Three years of operational history reconstructed from third-party APIs and several business sources, then reconciled into one relational foundation.

( A ) The challenge

The history existed, but not in a usable form

Three years of operational data sat behind third-party web APIs and across several business sources. Pulling it was the easy part. The difficulty was that the same customer, shipment, or driver appeared differently in each source, with missing values, duplicates, and inconsistent identifiers, and the relationships between records were not preserved on the way out.

Until that was resolved there was no reliable base for analytics or for machine learning. This is a data engineering problem, and it had to be finished before any modeling could be taken seriously.

( B ) The pipeline

From API responses to a relational foundation

Migration flow
Third-party web APIs and business sources↓ Extraction with checkpointing↓ Cleaning: missing values, duplicates, inconsistent identifiers↓ Reconciliation across sources↓ Relational data model design↓ Migration into PostgreSQL, ready for analytics and ML
Orchestration

Automated ETL with Apache Airflow and Spark, with Python and FastAPI components, so the process was repeatable and validated rather than a one-off script run.

Reconciliation

Cross-source relationship issues resolved with Pandas and SQL, so an entity has one identity and its links to other domains survive the migration.

Modeling

A relational model designed for the cleaned data, which is what turned a pile of exports into a structured dataset that downstream work can depend on.

( C ) Engineering decisions

Why it was built this way

Batch, not streaming

This is historical reconstruction, so correctness matters more than latency. Batch processing allows validation between stages and a rerun when a rule changes.

Relational, deliberately

The value of this data is in how the domains relate. A relational model enforces those links instead of leaving them to be rediscovered by every consumer.

Separate from the ML work

This migration and the ETA model share a data foundation but are different competencies. Keeping them separate makes it clear which problem each one solved.

( D ) Impact

What it made possible

An ML-ready dataset. Structured, reconciled history is what the ETA model was trained on.

Cross-domain questions became answerable. Links between domains survive in the model.

Repeatable process. Orchestrated pipelines can be rerun rather than redone by hand.

Improved traceability. Records carry consistent identity across sources.
