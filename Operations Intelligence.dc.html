Operations Intelligence

Two control problems that came from the same root cause: the numbers people reported on were not the numbers that actually happened.

Part 1 · E-commerce performance Part 2 · Financial operations & settlement

Both stories are described qualitatively. No performance metric has been published for either, so no numbers are claimed on this page.

Part 1 · ( A ) The challenge

An order that comes back is not a sale

E-commerce performance was being judged on order metrics reported by the ad platform. But in this operation an order is only a promise: it still has to be fulfilled, and it can come back as a return. Two campaigns can create the same number of orders and produce very different results once delivery is counted.

So the reported figure could overstate performance, and the correction lived in a different system entirely, in logistics and fulfillment outcomes rather than in advertising data.

Actual performance chain
Meta ads ↓ E-commerce order ↓ Logistics / fulfillment ↓ Delivered or returned ↓ Actual performance, per campaign
What I built

A connection between Meta advertising data, e-commerce orders, and the fulfillment result of each order, so profitability can be evaluated on what was actually delivered rather than on order creation.

Key decision

The outcome is attached to the order, not aggregated separately. Joining at the record level is what allows a campaign to be evaluated by its own delivered orders instead of a blended average.

Impact

Advertising performance became measurable against real operational outcomes, which changed what counted as a successful campaign.

Part 2 · ( A ) The challenge

Two currencies, and money that comes back in pieces

This one came out of requirement gathering with Accounting. Logistics collections and settlements happen in both USD and IQD, so balances that mixed the two were not meaningful, and reconciling them by hand was slow and easy to get wrong.

The second gap was in settlement control. A driver can return only part of the money linked to a collection or invoice, and a partially settled transaction has to stay visibly open. Otherwise the shortfall disappears into a total and nobody chases it.

Settlement flow
Collection / invoice ↓ Driver ↓ Partial settlement ↓ Outstanding balance, linked to that transaction ↓ Accounting alert for follow-up
Multi-currency workflow

Separate cashboxes per currency with their own transaction handling, so USD and IQD balances and settlements stay clearly separated and traceable rather than merged into one figure.

Driver debt tracking

Each outstanding balance is linked to the specific unsettled transaction that created it, and Accounting is alerted for follow-up, so a partial return is a tracked item rather than a discrepancy in a total.

Key decision

Debt is modeled per transaction, not per driver. A single driver total tells you something is missing but not which collection to ask about, which is the question Accounting actually needs answered.

( B ) My role

Across both parts

Requirement gathering with Accounting & E-commerce Process & control-gap analysis Solution design Data modeling Workflow implementation System integration

Both of these started as conversations, not tickets. Sitting with Accounting is how the currency split and the partial-settlement gap surfaced at all, and the e-commerce problem only became visible by comparing what advertising reported against what fulfillment recorded. Finding the gap was as much of the work as building the fix.
